Summary for L1 & L2 Team

Inject a failure to see the evidence-backed summary.

What We Give It

  • Pipeline failure event and logs (ADF, Databricks)
  • ServiceNow incident
  • Existing runbooks (manual run and troubleshooting steps)
  • Source/target schemas and pipeline configuration
  • Knowledge base documentation for RAG fallback

How It Processes

  • A failure creates a ServiceNow incident
  • LangGraph agent searches runbooks for a match
  • If found: runs the runbook checks in Python (failed activity, parameters, environment paths, linked services, logs, output files)
  • If not found: RAG with Azure OpenAI over the knowledge base
  • Builds an evidence-backed summary

What We Get Back

  • Likely root cause
  • Evidence and source (runbook or knowledge base)
  • Recommended next step
  • Confidence level
  • Summary attached to the incident for L1 & L2 review, reducing manual work for data engineers

DataGuardian AI

Evaluating Agentic AI for Evidence-Grounded Data-Ingestion Incident Diagnosis

Aryan Gulati · Associate Data Engineer  |  Ashish Jayantibhai Kadavla · Senior Data Engineer

Manulife · Manulife AI Research Conference 2026 · Research Poster (Work in Progress)

1. Problem

When a data-ingestion pipeline fails, data engineers manually check logs, follow runbooks, compare schemas and configuration, and search documentation. Much of this first-level investigation is repetitive and keeps engineers away from build work.

2. Research Question

Can an agentic AI that uses existing runbooks first, falls back to knowledge-based RAG, and grounds every finding in evidence give L1 & L2 teams a reliable incident summary and reduce manual work for data engineers?

3. Objectives

  • Build a working prototype
  • Automate runbook checks from a ServiceNow incident
  • Use RAG with Azure OpenAI when no runbook applies
  • Measure accuracy, groundedness and L1/L2 usefulness

5. Methodology

  • Controlled failure scenarios: schema change, wrong parameter/environment, missing linked service, duplicate key, datatype change, unclear errors
  • Each scenario has a known root cause
  • Runbook path and RAG fallback path both tested
  • Three approaches scored against ground truth

6. Data Sources

  • Synthetic pipeline events, logs and schemas
  • Public insurance claims dataset for demo ingestion
  • Sample runbooks modelled on standard manual-run and troubleshooting steps
  • Purpose-built knowledge base for RAG
  • No production customer data

8. Early Lessons

  • Existing runbooks are a strong, trusted first source
  • Use code, not the LLM, for exact checks
  • RAG is most useful when no runbook applies
  • Uncertain cases should escalate, not guess

9. Potential Business Impact

  • Operational: L1 & L2 receive a ready summary on the incident
  • Productivity: less manual first-level investigation for data engineers
  • Risk: evidence-backed, human-approved actions

Impact to be validated; not yet quantified.

10. Responsible AI

  • Privacy: synthetic/public data only
  • Governance: no autonomous reruns or production changes
  • Model risk: runbook-first, confidence gate, cited sources
  • Transparency: evidence shown in every summary

11. Next Steps

Complete prototype → test runbook and RAG paths on controlled scenarios → share preliminary findings at the conference → explore a governed pilot with sanitized runbooks and ServiceNow incident data together with L1 & L2 teams.
